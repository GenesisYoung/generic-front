## 3. 通用协议（拟定）

- 通过现有 `http` 客户端访问。正式API须校验登录；read权限沿用路由代码 `menu.order-audit-task.read`。
- 建议细分权限：同前缀 `.create`、`.update`、`.accept`、`.execute`、`.submit`、`.verify`、`.approve`、`.export`；**仅read代码已见路由，其余待后端配置**。ROOT也不得跳过本人核验／自批限制。
- 每次调用按任务归属、部门、协作范围校验。负责人下拉仅返回当前允许分派／查询的人；`canCreate` 和 `allowedActions` 由服务端按当前用户、数据与状态计算。前端隐藏按钮不是授权。
- ID统一字符串；枚举见下文；空值用 `null`，数组无数据用 `[]`；不以0、空串或浏览器时间冒充未知值。
- 时间传ISO-8601带时区格式，例如 `2026-11-20T08:00:00+08:00` 或UTC的 `Z`。数据库旧DATETIME没有时区，须先确认原业务时区再迁移。本页输入按浏览器时区，醒目标注；列表按metadata.timezone展示。工厂采用Asia/Shanghai只是需求建议，演示明确标为演示规则。
- GET成功200；新建201并返回Task；更新／动作200并返回Task。响应为**直接JSON对象**，不是 `{status, object}`。现有项目接口有多种格式，此处是新契约；后端若统一包装，须同步修改 `api.ts`。
- 写请求带 `Idempotency-Key: UUID` 和更新时的 `lockVersion`；服务端在同一事务完成状态转移、版本自增、成果快照及审计。
- 当前前端一次点击生成一个新幂等键，不自动重放写请求。超时不能判定写入失败；应重新查看详情核对。用户重新点击产生新键，服务端仍须通过来源唯一性、旧版本和状态限制防止重复成果。客户端提交时间、受理人、核验人均不可作为可信身份来源。
- 统一错误：`{code: string, message: string, fieldErrors?: [{field: string, message: string}], traceId?: string}`。不得返回SQL或凭证密钥。
- 状态码：400参数不合法，401未登录，403无权限／越界／本人核验，404记录不存在（也可用于遮蔽越界），409版本冲突／重复轮次／非法状态，422业务条件不满足，413附件过大，429限流，500系统失败；未实现返回404或501。

所有动作请求都需幂等键；服务端拒绝无关／受保护的字段，如客户端直接写acceptedAt、submittedAt、actor、status、effectiveDueAt。

Metadata响应：

```json
{
  "users": [{ "id": "42", "name": "授权责任人展示名" }],
  "canCreate": true,
  "timezone": null,
  "acceptanceRule": null,
  "completionRule": null
}
```

三个null明确表示未批准，受理必须拒绝。生产应保存获批规则版本并随成果冻结；字符串仅供前端展示，不能靠解析文案决定能否完成。

Query所有字段：`keyword: string`（订单号／任务编号，建议≤100字）、`ownerUserId: string|null`、`status: Status|null`、`dueFrom: datetime|空串`、`dueTo: datetime|空串`、`timing: string|null`、`page: integer≥1`、`size: 20|50|100`。Axios会省略null；空串视为无筛选。时间区间包含两端，过滤effectiveDueAt，非接收时间；设置区间后排除期限为空的未受理任务。工作类型后端固定A1，不接受客户端改指标。

`timing`暂沿用界面值：未受理、逾期未结、期限内未结、逾期已交付、按期已交付。后端先按相同定义过滤再分页。建议正式联调前改成稳定枚举并同时修改前端，不能只改一端。

Page响应：`{items: Task[], total: nonnegative integer, sourceChecked: boolean, asOf: datetime}`。total是**筛选后的全量总数**；sourceChecked表示该授权范围来源是否已核对，不等于items非空。asOf为本次查询服务端时刻，页面用它显示期限事实，防止各行取时不一致。长时间停留后手动刷新更新。

排序规则：已受理、未交付且未撤销的任务先；组内按effectiveDueAt升序（逾期自然靠前），其余再按截止时间、稳定id排序；null期限排最后。服务端排序及分页必须稳定。

核验映射：PASS／FAIL→VERIFIED并分别展示符合／不符合；NEED_PROOF→RETURNED；DISPUTED保持SUBMITTED并显示归责争议。争议不应覆盖客观事实。SUBMITTED后的新版需要重新独立核验。

按期事实：未受理不显示逾期；有实际完成时比较completedAt≤effectiveDueAt；未完成则比较asOf；阻塞不暂停。该标签不说明成果有效、不保证纳入月评。正式绩效须按冻结完成规则、历史核验和获批归责计算，前端不自行结算。

响应为更新后的完整Task，其中status=TODO、lockVersion=4，acceptedAt为服务端时间，originalDueAt／effectiveDueAt为批准期限。缺资料示例：HTTP422，`{"code":"REQUIRED_MATERIAL_MISSING","message":"必备包装资料尚未齐备","fieldErrors":[{"field":"materials","message":"包装规格缺尺寸"}]}`。

## 7. 业务／技术待确认清单

1. **必备资料**：不同订单类型的清单、必备规则、谁能确认完整、凭证要求；空清单不能当作齐备。资料已交与资料审核合格是否分层。
2. **完成条件**：合格成果交付，还是主管业务确认通过；确认前不能正式计分。独立绩效核验与主管业务确认需两类记录；目前页面录入成果和独立核验，业务确认需配套接口和界面。
3. **受理权限与时限**：哪类主管／独立受理角色；时限算法、工作日历、时区、补录及回溯政策；是否允许批准已过期的截止时间。客户端不擅自设默认时限。
4. **轮次**：从一单一条改为订单＋轮次；获批重评凭证如何关联，哪些轮次纳入月评；当前新增表单可输入轮次，但后端必须拒绝未获批重评。
5. **旧数据迁移**：谁认领、状态未知如何展示、资料备注如何拆分、旧批准凭证实际含义、旧DATETIME时区；历史空值不得自动补“符合”。拿到修订SQL后再编写迁移，本次不修改后端DDL。
6. **用户／部门范围与权限码**：员工、协作、主管和领导的数据范围；现有路由read码能否对应已配置权限；全部写权限、规则权限、导出权限需建立后端映射。
7. **文件协议**：现有approval_proof的50字是文件ID、路径还是编号；需要上传和预览时是否复用现有能力。前端evidenceRef暂为文本，不意味着文件已保存。
8. **计分**：按期限月份的分母规则、成果版本选择、争议、撤销、受理后阻塞及归责调整，以获批规则及不可变快照为准；本页不自动改数量、采购或库存，也不自动产生绩效结论。
9. **界面协议建议**：字数限制、资料项最大条数、历史分页阈值、负责人远程查询、稳定timing枚举及统一响应包装，应在真实接口联调前敲定。
